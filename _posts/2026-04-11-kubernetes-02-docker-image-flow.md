컨테이너를 실제로 사용할 때 가장 많이 만나는 도구는 Docker다. Docker는 애플리케이션을 이미지로 만들고, 그 이미지를 어디서든 실행할 수 있게 해준다. 여기서 중요한 포인트는 실행 방식이 단순해진다는 점이다.

## Dockerfile은 실행 환경의 설계도다

Dockerfile은 애플리케이션을 어떤 환경에서 실행할지 적는 파일이다. 예를 들어 Python 애플리케이션이라면 베이스 이미지를 Python으로 잡고, 소스 코드를 복사하고, 필요한 패키지를 설치하고, 실행 명령을 정의한다.

```dockerfile
FROM python:3.11
WORKDIR /app
COPY . .
RUN pip install -r requirements.txt
CMD ["python", "app.py"]
```

이 파일 하나로 애플리케이션 실행 환경을 설명할 수 있다. 누가 실행하든 같은 Dockerfile로 이미지를 만들면 같은 방식으로 실행할 수 있다.

## Build, Ship, Run

Docker의 흐름은 크게 세 단계로 볼 수 있다.

첫 번째는 Build다. Dockerfile을 기반으로 이미지를 만든다.

```bash
docker build -t myapp:1.0 .
```

두 번째는 Ship이다. 만든 이미지를 Registry에 올려 다른 환경에서 가져다 쓸 수 있게 한다.

```bash
docker push myrepo/myapp:1.0
```

세 번째는 Run이다. 이미지를 받아 실제 컨테이너로 실행한다.

```bash
docker run myrepo/myapp:1.0
```

## 배포와 롤백이 쉬워지는 이유

컨테이너 이미지는 애플리케이션 코드와 실행 환경을 하나의 스냅샷처럼 묶는다. 그래서 서버마다 직접 git pull을 하고, 패키지를 설치하고, 설정을 맞추는 과정을 줄일 수 있다. 배포는 새 이미지를 실행하는 일이 되고, 롤백은 이전 이미지를 다시 실행하는 일이 된다.

이 점은 운영에서 매우 중요하다. 장애가 났을 때 원인을 찾기 전이라도 이전 버전으로 빠르게 되돌릴 수 있기 때문이다.

## 쿠버네티스와 연결되는 지점

Docker는 컨테이너를 만들고 실행하는 문제를 단순하게 만든다. 하지만 컨테이너가 수십 개, 수백 개로 늘어나면 다른 문제가 생긴다. 어떤 서버에 컨테이너를 띄울지, 죽은 컨테이너를 어떻게 다시 띄울지, 외부 요청을 어디로 보낼지 같은 문제다.

이 지점부터 쿠버네티스가 필요해진다. Docker가 컨테이너의 실행 단위를 만든다면, 쿠버네티스는 그 실행 단위를 클러스터 전체에서 관리한다.
